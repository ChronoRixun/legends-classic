# scripts

## SUMMARY
I built a converter that rewrites every XML1 script (1318 bundle scripts plus 90 scripts that exist only in the assets zip) into a form XML2 PC can run, and it checks out against the functions XMen2.exe actually registers. XML2's function table is at 0x68a908 (289 entries) plus a builtins table at 0x6903d8 (19): 308 functions. XML1's are at 0x3d0b88 (197) and 0x3d5620 (16): 213. Entries have the same layout in both: {func, name, ret-sig, arg-sig}. The script language itself is unchanged between the games: same line parser, same keywords (if/elif/elseif/else/endif/def), CRLF-split files, and names and keywords compared case-insensitively (_stricmp).

The XML2 parser silently drops any line whose function is unknown, whose argument count differs, or whose literal type is wrong. Copied unchanged, 1616 XML1 script lines would be dropped. After the rewrite, 14 remain, and all of them are lines XML1 itself already dropped (in dead developer scripts).

One stated fact is wrong: 143/152 was counted against XML2's script files, not its registration table. XML2 registers only 129 of the 152 functions XML1 scripts use. The other 23 include screenFade (396 calls), the popup API (~470 calls) and get/setMissionVar and get/setGameVar.

Persistence is the main difference. XML1's mission vars and flags use the same store and the same code as XML2's zone vars, but XML2 clears that store on every zone load. XML1 only cleared it when you entered a zone in a different map directory. XML2 also has no way to set a whole integer game var; game vars can only be set one bit at a time with setGameFlag. So mission flags become game flags with the same name and bit numbers. Other mission and game vars are stored as bit fields in x1v##/x1g## game vars (signed where needed). Counters only used inside one zone become zone vars. Mission-scoped bits are cleared when the owning mission starts. This uses 41 of XML2's 96 free game-var slots, and at most 7 zone vars in any one zone.

XML2's beginMission is a no-op: it sends a console command, beginmission, that XMen2.exe never registers. So every mission start becomes generated code: setCurrentAct, objective resets, then the mission's start script or map load. XML1's 101 missions are packed into 9 XML2 mission files (acts): 177 objectives, at most 47 per act, within XML2's hard caps of 25 files, 299 objectives and 75 per act. XML2's restorelastzone uses the same handler code as XML1's endSideMission. XML2's unlockCharacter calls the same unlock method as XML1's setInCampaign. XML1's loadMap sends the same console command as XML2's loadMapKeepTeam, while XML2's own loadMap sends a command that isn't registered.

Popup dialogs built in script become 92 generated dialog files. Their option scripts run through the console as "runscript <code>", so the generated code contains no spaces.

To use the output: install it with forced overwrite, apply out/inline_rewrites.json while converting conversations, zones and dialogs, and add the entries in out/zone_extra_files.json to each zone package. Four things can't be reproduced with scripts alone and need an in-game test or a design decision: forcing specific heroes per mission, adding a hero mid-mission, solo mode, and the exact return point after side missions.

## PLAN
1. Regenerate outputs: cd research/scripts; python mission_plan.py; python rewrite_scripts.py; python verify_output.py. All inputs are read-only XML1/XML2 files plus the JSON evidence files in this folder. Output goes to research/scripts/out/.
2. Install scripts: Copy out/scripts/** to <xml2>/Scripts/ with force overwrite, including the 25 XML2 path collisions (common/*). Decide menus/intro_normal.py and menus/main_back_*.py separately, since they replace XML2's boot intro and main-menu background. Change convert_zone.py to take scripts from out/scripts instead of xml1_loose (it currently copies raw XML1 scripts with convert_file).
3. Install generated data: out/dialogs/x1/*.XMLB and .engb go to <xml2>/Dialogs/x1/ (engine prefixes 'dialogs/'; see 0x5ebc57). out/data/missions/missions.XMLB and x1_act01..09.XMLB/.engb replace Data/missions/. Attribute names are already lower-case and sorted.
4. Apply inline rewrites in the data converters: When converting conversations/*.eng, maps/*.eng entity attributes and dialogs/*.eng, replace each attribute value that is a key in out/inline_rewrites.json (129 entries) with its value. Also normalise backslashes to '/' and lower-case script-path references.
5. Package generated files per zone: For every zone, add the entries in out/zone_extra_files.json to its PKGB: a <script> entry for scripts/x1/..., and an xml/dialog entry for dialogs/x1/pNNN. XML2 packages every script a zone can run (e.g. military1.PKGB lists act3/military/go_to_madri used by a dialog).
6. Zone act on entry: setCurrentAct was injected into 73 zone scripts. 49 zones have no zone script: set the world entity's zonescript to x1/zones/<zone> (generated). 22 zones belong to missions in different acts and get no call; they rely on beginMission. See out/zone_acts.json.
7. In-game verification (orchestrator): Test in the order listed in open_questions: (1) a popup dialog with runscript options, e.g. mansion/man2/chose_mission; (2) the beginMission chain alison -> mansion1, checking objectives appear; (3) a packed var surviving a zone change and a save/load, e.g. sewers pstatus; (4) endSideMission from jug_fb or sent_fb; (5) loadMapKeepTeam vs loadMap.
8. Optional exe patch (only if needed): For exact XML1 variable semantics: in XMen2.exe 0x49fe70, clear zone vars only when the zone directory changes (XML1 0x824c0 logic). The storage then simplifies to MissionVar -> ZoneVar and MissionFlag -> ZoneFlag. A second call to 0x4d75a0 with an extra table could re-register getGameVar/setGameVar and addHero. Not required by the current rewrite.

## RISKS
- Game-flag emulation changes lifetime: XML1 cleared mission vars when the player entered a different map directory; the rewrite clears them when the owning mission starts. After a side-mission return, XML1 might have reset the parent's vars; the rewrite keeps them. 25 variable-valued counters are XML2 zone vars and reset if the player leaves the zone mid-sequence (XML1 kept them while you stayed in the same directory).
- Packed counters are 8 bits (0..255, or -128..127 for the one signed var, 'stage'); larger runtime values wrap. Variables holding entity IDs or health are kept as zone vars to avoid this.
- The mission plan uses acts 1..9. XML2 UI or act-indexed data may assume acts 1..5, and changing the act runs 0x46a1a0, which purges item categories 3 and 4.
- Hero requirements per mission (REQUIREDHERO, RESTRICTEDHERO, maxheros=1, teamselect) can't be enforced from XML2 scripts. The rewrite only unlocks the required heroes and keeps the current team (loadMapKeepTeam), or uses loadMapChooseTeam when teamselect is true.
- addHero is emulated by unlock plus opening the team menu (extractionPointLite). Solo mode (18 inline enterSoloMode in astral/arbiter bridge triggers, 4 exitSoloMode) is removed, which may change puzzle behaviour.
- The mapping of extractionPointLite's 5 XML1 flag arguments to XML2's 3 (keeping the first three) is unverified.
- endSideMission returns to the caller zone's default start (loadZone(zone, '')), not the exact position; jug_fb and dr_mag1 return to mansion/man2/subbasement2.
- The loadMap -> loadMapKeepTeam decision rests on static evidence that 'loadmapaddteam' is not a registered console command.
- The 25 path collisions with XML2's Scripts folder (common/*, menus/*) must be force-overwritten, or XML2's unconverted XML1 leftovers will run instead.

### plan problems
- Unaddressed script-engine capacity. XMen2.exe has fixed global pools: 620 instruction nodes (0x4d7e6e, one per parsed statement allocated at 0x4d978a, freed on failure at 0x4da382), 1556 int/float values (0x4d6578 cmp 0x614), 120 script objects (0x4d86d1) and a compiled-script cache (0x4d6980, reset in 0x4d7fa0). Bit-packing inflates packaged zone scripts 1.44x (14824 -> 21286 statements). mastermold2 goes 421 -> 906 statements (core_on/off 23 -> 83 lines each, from the 8-bit 'corecount'), and 4 zones exceed XML2's largest retail zone (mikhail, 530). Suggestively, both games' largest zones sit just under their own node pool (XML1 pool 0x1cc=460 at 0xcadc1 vs XML1 max 421; XML2 620 vs 530), so per-zone residency may be a real limit. The plan only compares single-file line counts (165 vs 182). Test mastermold2 early. Mitigations: narrower counters, or the optional exe patch at 0x49fe70, which would remove the packing.
- Zone act coverage is overstated. The plan says to give the 49 zones without a zone script zonescript=x1/zones/<zone>, but only 27 such scripts were generated. The other 22 are multi-act or no-act (sewers1_1_3/1_2_x, nuke1_x/2_2x, asteroid2_x, haarp2_2/2_3, mansion7_x, mount, etc.). Separately, 22 zones with scripts get no injection. So 44 zones set no act on entry. Many conflicts come from packing 32 boss_*/demo/test missions into act 9, where they reuse campaign zones.
- Installing 'with forced overwrite' into <xml2>/Scripts and replacing Data/missions/missions.XMLB is only safe in a dedicated XML2 copy. 11 of the 25 colliding scripts differ from XML2's copies, and common/kingofhillxpip.py is used by 51 XML2 files (getZoneVar('xpips') would become x1v01 bits). The plan should mandate a separate install or namespace the XML1 copies (e.g. x1/common/...) and rewrite their references.
- Validation is case-insensitive, but XMen2.exe function lookup is case-sensitive (interned raw-byte hash 0x41a340 + repe cmpsb 0x419d0b). validate_lines and verify_output.py should compare exact case. Currently only 1 dead line is affected.
- Dead-end live dialog: x1/p091 and p092 (Forge on Muir Island, spokewithforge.py <- 1_6_4_meet_forge.eng) run muir_is/muir1/loadSewers and loadBlackbird, which do not exist. They need a real target (e.g. the next mission's begin_ script or loadMapKeepTeam) or progression stops.
- addHero 'no XML2 equivalent' rests on vtbl_usage.py comparing slot offsets across different vtable layouts. That comparison proves nothing, so the addHero workaround (unlock + extractionPointLite) should not be treated as the only option until XML2's team/party functions are actually checked.
- Console constraints the plan does not mention: at most 2 pending commands (0x55c426) and 127-char commands (0x55c42f). Current output complies, except the dead missions/sewers_start.py, which sends blackbirdMenu + 2 startMovie with no wait. Any future generated chains (e.g. a real beginSideMission emulation) must respect both limits.
- convert_zone.py's add_zoneinfo writes act='1' for every XML1 zone, while the plan assigns acts 1..9 and XML2 zoneinfo uses 1..5. The plan does not reconcile this. The observed zoneinfo load path (0x484fb9) reads only name/loading/savename, so impact is unknown and needs checking.
- Lifetime semantics differ, as the researcher notes: packed vars are cleared at owning-mission start rather than on directory change, and single-zone counters become XML2 zone vars that reset on every zone load. The in-game tests should cover a re-entered zone within the same XML1 directory, not only a save/load.
